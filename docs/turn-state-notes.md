# Turn-State 机制

[返回首页](../README.md)

本文说明当前代码行为。早期关于 Token 池、每条请求消耗一个 Token、30 分钟自动失效的实验方案，已不适用于当前实现。

## 获取与缓存

应用使用当前工作目录中的 ChatGPT 凭据，通过所选出站代理向上游 `/responses` 发起轻量请求，从响应头读取 `x-codex-turn-state`。探针使用与 Codex TUI 自洽的 `User-Agent`、`originator`、`version`，每次生成新的 `session_id`，请求体为固定的 `ping/pong` 轻量交互。

- 全局单发获取；每轮只选择一个需要刷新的模型，多个模型按轮次轮询，不产生十路突发。
- 请求强制使用 HTTP/1.1、新连接和 `Connection: close`；认证信息不会跟随重定向。
- 只有 HTTP 200 下长度精确匹配该模型请求开始时绑定长度、前缀正确、时间戳可解析且未超过预取年龄的候选值才会入池；312、未来时间戳和其他长度仅记录后拒绝。
- Token 按模型分别缓存，内存与本地文件同步，启动时尝试恢复；不同模型不可互用。
- 未命中目标长度时 6 秒后重试；连接阶段失败会在同一模型内最多尝试 4 次，每次仍间隔 6 秒。429/503 与连接失败按全局线路退避 30 秒，401 按账号全局冷却 5 分钟；403 只让对应模型冷却 30 秒，其他模型仍可在共享单发与 6 秒间隔约束下继续获取。有可用票据时约每 30 秒巡检。
- 票据超过 35 分钟开始预取，40 分钟后不再注入；预取失败期间仍可使用尚未到 40 分钟的旧票。
- 切换工作目录、出站地址、出站模式或上游配置等会清空缓存并重新获取。

获取成功必须同时满足 HTTP 200、响应头票据合法且匹配该模型当前绑定长度。探测使用账号授权发起真实请求，会消耗上游请求资源，不应视为无成本的本地检查。

## 手动采集

主页面可从当前 Codex 可见模型缓存和配置模型中选择目标，立即启动一轮采集，无需等待 Codex 先发送业务请求。手动任务与被动发现共用同一个单发队列、6 秒间隔和错误冷却，不会建立额外探针循环。

- 已有新鲜匹配票据时不会重复启动。
- 同一时间只运行一个手动任务；开始其他模型前需先停止当前任务。
- 命中目标长度后任务自动完成，取得的票据继续保留。
- 用户可以中途停止；停止不会删除已经取得的票据，也不会停止同模型的被动自动维护。
- 切换账号、工作目录或获取线路会取消未完成的手动任务；旧在途结果仍受账号和配置代际校验，不会写入新环境。
- 手动任务只存在于当前进程，退出应用后不恢复。

## 请求处理

| 流量 | 当前规则 |
| --- | --- |
| HTTP `POST`，路径包含 `/responses` | 默认仅在客户端已携带 Turn-State 时，用同账号、同模型的有效缓存替换；可切换下述策略 |
| HTTP 客户端未携带 Turn-State | 保持未携带状态，不据此判断是否首次请求 |
| WebSocket 升级请求 | 返回 426，让 Codex 客户端回退到 HTTP SSE |
| 上游业务响应 | 不进入本地票据池；本次注入的票据仍是当前票且明确返回 312 时，清除对应模型旧票据并唤醒重新获取 |

缓存会重复使用，不会按请求消耗；代理层仍会按 HTTP 转发要求处理连接相关头。

主页面的「State 处理策略」自动保存到配置，旧配置默认使用 `preserve`：

| 策略 | 行为 |
| --- | --- |
| 无可用凭证时保留原值 `preserve` | 优先替换；没有匹配缓存或模型无法识别时保留客户端 state。Kit 切换请求账号后仍会移除旧账号 state。 |
| 无可用凭证时持续等待 `wait` | 优先替换；没有匹配缓存则等待后台获取同账号、同模型的有效凭证，无固定超时。客户端断开会取消等待，不会之后补发。 |
| 无可用凭证时剥离 `strip` | 优先替换；没有匹配缓存或模型无法识别时删除请求中的 state。 |
| 不替换 `passthrough` | 始终原样保留客户端 state，有有效缓存也不替换、不按账号变化删除 state。 |
| 全部剥离 `strip_all` | 所有业务请求发出前均删除 state，包括存在有效缓存的情况以及 `/models` 等其他路径。 |

前三种策略不向原本未携带 state 的请求主动注入。后两种仅控制 state，账号认证仍遵循 Kit 的登录转发规则；所有策略均保持上游响应中的 state 原样返回，后台凭证获取继续运行。

等待不会绕过后台获取的冷却或单发调度，也不会拿其他账号、其他模型或已过期的票据代替。等待策略下，`POST /responses` 请求明确携带的账号 ID 或 Bearer 与当前登录凭据冲突时，即使存在缓存或未携带 State，也立即返回 409「账号凭据不匹配」，不等待、不转发；比较发生在 Kit 覆盖鉴权头之前，未显式携带身份并由 Kit 补齐的请求不算冲突。模型无法识别时返回 422；账号无法识别，或等待期间登录账号、线路、策略发生变化时返回 409，请求不会发往业务上游。修改绑定长度后继续等待当前绑定匹配的凭证。尚在等待凭证的请求不计入已发往上游的并发数和 RPM。

## 当前边界

- **客户端未携带时保持无票据**：不会为未携带 Turn-State 的请求主动注入；这不代表该请求一定是本轮首次请求。已携带但无法识别模型时按所选策略保留、剥离或拒绝等待。
- **账号快照保持一致**：每个业务请求使用同一份凭据快照完成票据池账号校验和 Kit 鉴权覆盖；客户端原头与当前官方账号不一致时不注入缓存票据。
- **业务响应不进入票池**：真实业务响应中的 Turn-State 只用于日志，不会覆盖后台探针取得的模型票据。
- **代理 URL 不做会话改写**：每次探针使用新 client 和新连接；动态住宅代理是否更换出口由代理供应商决定。
- **长度是项目筛选规则**：界面中的“292”“312/降智”是项目标签，不是模型能力或计算档位的官方指标。

本工具以缓解使用问题为目标，不改变账号套餐、配额或模型本身，也不保证消除上游过载。历史实验中的地区、长度和单题回答差异不足以证明模型能力变化，不能作为稳定效果承诺。
